# Canvas 2.0 — MVP Design Spec

**Date:** 2026-06-19
**Status:** Draft
**Target:** Executive Assistant, Session view

---

## 1. Overview

### Problem
The agent currently has no visual workspace. The user and agent operate through text-only chat. Files, emails, todos, contacts, and notes are invisible unless the agent explicitly mentions them. There is no shared surface for awareness, collaboration, or visual expression.

### Solution
Introduce a **Session view** that replaces the current Workspace panel. Each session has a left-side chat panel and a right-side workspace with live HTML widgets (Email, Todos, Contacts, Files, Notes) and an agent-created Canvas. All widgets share the same data layer as the agent's tools — what the agent sees, the user sees, and vice versa.

## 2. Sidebar Changes: Sessions within Chat

### Change
| Before | After |
|--------|-------|
| 💬 Chat | 💬 Chat *(now supports multiple sessions)* |
| 🔧 Tools | 🔧 Tools |
| 📋 Skills | 📋 Skills |
| 📝 Subagents | 📝 Subagents |
| 🎨 Workspace | *(removed)* |
| ⚙️ Settings | ⚙️ Settings |

### Sessions (within Chat)
`Session` is the organizational unit. A user can have multiple sessions within Chat (like browser tabs), each with:
- Its own conversation history (isolated via CoreMem `session_id`)
- Its own workspace state (open tabs, selected items, canvas surfaces)
- Independent scroll positions and widget state

Sessions are created when the user clicks "+" in the Chat header, or when the agent initiates a new context via `[NEW_SESSION]` directive.

### CoreMem session wiring
CoreMem's `MemoryCore` already supports `session_id` in both `ingest()` and `fetch()`. The gap is entirely at the EA storage layer:

**Current state:**
- WS handler generates `session_id = str(uuid.uuid4())[:8]` per connection but buries it in `metadata` JSON — never passes it to the `session_id` column
- `MessageStore.add_message()` has **no `session_id` parameter** — never calls `self._core.ingest(session_id=...)`
- `MessageStore.get_messages_by_session_id()` exists but returns nothing because column is always `""`

**Changes needed:**
- `MessageStore.add_message()` and `add_message_with_embedding()` gain a `session_id: str | None = None` parameter, passed through to `self._core.ingest(session_id=session_id)`
- `MessageStore.get_messages()` gains optional `session_id` filter
- WS handler passes `session_id` to `add_message()` calls instead of stuffing it in `metadata`
- WS handler accepts `session_id` from the client (via query param or first WS message), falling back to generating a new one

## 4. Canvas Tab

### Mechanism (unchanged from current)
Agent outputs HTML inside `` ```html:canvas ``` `` fences. Backend extracts, sends `canvas_update` over WS, Flutter renders in WebView.

### Changes
- Canvas surfaces are now **per-session**, not per-workspace
- Agent-generated HTML inherits EA theme via `ea-tokens.css` (shared CSS token file)
- Canvas is always the first tab by default (user can reorder)

## 5. Widgets: Email, Todos, Contacts, Files, Notes

### Architecture
Widgets are **fixed HTML templates** served by the backend. They consume existing REST APIs — no new endpoints.

```
User clicks Email tab
  │
  ▼
Flutter fetches GET /widget/email
  │
  ▼
Backend renders HTML template with data from email_list tool
  │
  ▼
HTML returned, rendered inline in workspace panel
```

### Existing APIs each widget consumes
| Widget | API calls |
|--------|-----------|
| Email | `GET /email/list` → inbox, `GET /email/get/{id}` → detail |
| Todos | `GET /todos/list` |
| Contacts | `GET /contacts/list`, `GET /contacts/get/{id}` |
| Files | `GET /files/list`, `GET /files/read` (existing REST endpoints) |
| Notes | `GET /files/list` filtered to notes dir `GET /files/read` |

### Widget state
- Widgets are **read-only views** of tool data (for now)
- Co-edit (turn-based) is built separately for Notes, Email body, text files — see Section 7
- Widget data refreshes when:
  - Tab is switched to
  - Agent calls a mutating tool and includes `[WIDGET_REFRESH:<tab>]` in response
  - User manually refreshes

### Styling
- All widgets use `ea-tokens.css` CSS custom properties
- Widget HTML is served with minimal chrome (just the data)
- The workspace panel provides the container chrome (padding, scroll)

## 6. Agent Integration

### Workspace context injection
Before each LLM turn, the backend injects a compact workspace state block:

```
[Chat: Canvas tab — 2 surfaces]
```

Context is **minimal** — just the active tab and a count/identifier of what's visible. The agent uses existing tools to fetch details if needed.

### Agent directives in text responses
The agent can control the workspace by including directives in its text output:

| Directive | Effect |
|-----------|--------|
| `[SWITCH_TAB:email]` | Switch workspace to Email tab (animated) |
| `[WIDGET_REFRESH:email]` | Re-fetch and re-render Email widget |
| `[WIDGET_REFRESH]` | Re-fetch all widgets |
| `[NEW_SESSION]` | Open a new session (new conversation + fresh workspace) |

Directives are stripped from display text (same as canvas fence stripping).

### Agent tool usage
No new tools. The agent continues using existing tools (`email_get`, `email_send`, `todos_list`, etc.) — the workspace widget automatically reflects changes via `[WIDGET_REFRESH]`.

## 7. Co-edit: Notes, Email Body, Text Files

### Model: Turn-based with transitions
1. **User writes** in a text widget (Notes, Email compose, File edit)
2. User asks agent to review/revise
3. **Agent responds** with a proposed edit (inline diff or replacement text)
4. **Transition animation** — the content smoothly transitions from old to proposed (e.g., highlight changed lines, 280ms ease)
5. **User accepts or rejects** the proposed change

### Visual treatment
- Changes are highlighted with a subtle green pulse animation
- Accept/reject buttons appear inline near the changed content
- The transition uses the EA motion curve: `cubic-bezier(0.34, 1.56, 0.64, 1)` (slight spring)

### Implementation approach (Phase 4)
1. Agent proposes a revision in chat text (inline diff or replacement)
2. An "Apply" button appears next to the proposed edit in the relevant widget
3. User clicks "Apply" → backend writes the change via tool (`files_write` / `email_save_draft`)
4. `[WIDGET_REFRESH]` updates the widget to show the new content
5. Transition animation highlights the changed area (280ms ease)

Full collaborative editing (real-time sync) is future.

## 8. Technology

### Frontend
- **Flutter** app with WebView for workspace panel
- **HTML/CSS** widgets served from backend
- **WebSocket** for chat + canvas updates (existing)
- **HTTP** for widget data fetches (existing REST APIs)

### Backend
- New route: `GET /widget/{type}` — serves widget HTML (rendered from template + tool data)
- New shared CSS: `src/http/static/ea-tokens.css` — EA design tokens as CSS custom properties
- Workspace context injection in conversation router
- Directive parsing in WS handler (strips `[SWITCH_TAB:*]`, `[WIDGET_REFRESH:*]`)

### Data layer
All existing. SQLite per user, same tool layer the agent uses.

## 9. Session State (Multiple Sessions)

Each session has independent state managed in the Flutter app:

```
Session {
  id: string
  conversation: Message[]
  workspace: {
    tabOrder: string[]          // user's drag-reordered tabs
    activeTab: string
    canvasSurfaces: Surface[]   // agent-generated HTML
    widgetState: {
      email: { selectedId, scrollPos, detailOpen }
      todos: { scrollPos }
      contacts: { selectedId }
      files: { currentPath }
      notes: { currentPath, content }
    }
  }
}
```

State persists in-memory (app lifetime). Long-term persistence to SQLite or SharedPreferences is future.

## 11. Implementation Phases

### Phase 1: Foundation
- Create `src/http/static/ea-tokens.css` with EA design tokens as CSS custom properties
- Create `GET /widget/{type}` route serving HTML templates
- Wire workspace context injection into conversation router
- Add directive parsing to WS handler (`[SWITCH_TAB]`, `[WIDGET_REFRESH]`, `[NEW_SESSION]`)
- Wire `session_id` through message storage for session-isolated conversation history

### Phase 2: Widgets
- Email widget (inbox list + detail view)
- Todos widget (list + checkbox toggle)
- Contacts widget (list + detail)
- Files widget (directory listing + file viewer for text files)
- Each widget consumes the existing REST API
- Widget data fetched on tab activation via `GET /widget/{type}`

### Phase 3: Canvas + Session
- Canvas surfaces per-session (not per-workspace)
- Tab bar: scrollable, draggable, animated
- Multiple session support in Flutter

### Phase 4: Co-edit
- Notes widget with turn-based editing
- Email body co-edit
- Text file co-edit

---

## 12. Security & Auth

- Widget API uses same auth as existing REST endpoints (Bearer token or localhost bypass)
- No new data access — widgets consume the same tools the agent calls
- Session state is client-side only (no server-side session storage for MVP)
